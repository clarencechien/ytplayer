# 實驗：非英文 ASR 的轉寫可信度（日文）

> 目的：驗證 `handoff-append-01` §C 的假設 —— 「日文／韓文 ASR 明顯較差…**轉寫本身不可信**，
> 修稿等於在修錯的文字，翻出來錯上加錯」—— 在 2026 年是否仍成立。
> 該結論寫 handoff 時是**假設**（推測來自 kvsplayer 的韓文經驗），從未在本專案量測過。
> 日期：2026-08-13。樣本：`9gHJwbSHPus`（トバログ／Galaxy Z Fold8 評測，31 分鐘）。

---

## 1. 樣本與方法

這支影片的軌別結構罕見地適合當實驗檯：

- 創作者（日本人）手動上傳 **14 條翻譯軌**（zh-TW/zh-HK/zh-CN、en、ko、de、fr、es、ru、th、it、id、pt-BR）
- 但**日文本身只有 ASR**（`a.ja`）—— 自己母語靠 ASR、翻譯軌才手工上，是常見做法

因此**純 WER（日文人工 vs 日文 ASR）做不到**，改用兩條路：

| 資料 | 檔案 | 角色 |
|---|---|---|
| 創作者人工繁中軌（521 cues） | `phase0/out/ref-9gHJwbSHPus-zhHant.json` | 意思的 ground truth |
| 人工英文軌 → 本 pipeline 譯文（520 cues） | `phase0/out/ctrl-9gHJwbSHPus-enUS.json` | 控制組（輸入絕對可信） |
| 日文 ASR 原始軌（686 cues） | `phase0/out/src-9gHJwbSHPus-jaAsr.json` | 受測輸入 |

比對方式：**30 秒窗口**把兩邊各自串接後比對語意（ASR 的 cue 是短碎片、人工中文是長語意塊，
逐句對齊會產生假性落差）。

## 3. 判讀

**§C 的結論對日文過強，前提不成立。**

§C 的論證是：「錯的是聽寫 → 修稿在修錯的文字 → 錯上加錯」。但實測顯示錯誤**不是瀰漫性的**，
而是**窄而系統性**地集中在專有名詞。而這恰恰是修稿 pass 的設計標的 —— 它的 prompt 明寫
「依上下文修正明顯聽錯的詞，特別是人名、公司、產品、術語」，而且它拿得到影片標題：

```
【実際どう？】Galaxy Z Fold8レビュー！ じっくり使ってわかった良い点＆残念な点
```

正確答案就寫在脈絡裡。所以修稿不是「在修錯的文字」，是**在修可修的文字**。

### 誠實的邊界

1. **只量了日文**。§C 同時涵蓋韓文，本實驗沒有韓文樣本 —— 韓文的結論仍是未驗證的假設
2. ~~**端到端未驗證**~~ → **2026-08-13 已實測通過**（Queues 架構重建後，見 §4.4）：
   修稿確實把 `Zold8` 全數修回 `Galaxy Z Fold8`（6→0）、`アスペクト費`→`比` 也修正
3. 24:00 附近日文與中文明顯不同 —— 判讀為**人工譯者連畫面字卡也翻了**（10bit Log），
   ASR 只聽得到旁白。這不是 ASR 錯誤，是兩者記錄的維度不同

共 42 次 LLM 呼叫、273,617 tokens（每片上限 500k 內），每步進度落地可視。

## 4. 過程中發現的基礎設施限制（比實驗本身更重要）

反覆嘗試跑日文翻譯時暴露了執行環境的硬限制：

| 路徑 | 工作量 | 結果 |
|---|---|---|
| 手動 `/translate?wait=1`（同步） | 686 cues | 5 分鐘被客戶端逾時切斷 → Worker 被取消 |
| 手動 `/translate`（`ctx.waitUntil` 非同步） | 686 cues | 無任何產出、無錯誤紀錄 |
| 同上 | **150 cues**（切片） | 同樣無產出 |
| 同上 | **瞬間失敗**（無 source） | **91 毫秒寫下紀錄 ✓** |
| **cron**（scheduled handler） | 520 cues | **成功 ✓**（07:52 完成英文軌） |

隔離測試證明 `waitUntil` 機制本身正常（瞬間工作有紀錄），但**只要是真實翻譯工作量就被中止**。
對照 cron 能完成 520 句 —— 結論：

> **fetch handler（含 waitUntil）跑不了本專案的 pipeline，長工作只有 scheduled handler 能承載。**

推論的次生問題：cron 開工前寫 `.translating` 鎖、結束時於 `finally` 刪除；若 Worker 被外部
中止，`finally` 不會執行 → **鎖殘留 10 分鐘** → 期間所有 cron 跳過該片 → 過期後重試 → 再被砍，
形成安靜的迴圈。這與觀察到的現象一致（日文軌始終沒被 cron 處理）。

### 4.2 成本事故（2026-08-13，NT$1000+）

上述鎖漏迴圈**不只是理論**，實際燒掉了超過 NT$1000 的 Gemini 費用。事故鏈：

1. 08:44 ingest 日文 ASR 切片（150 cues）→ source 比 07:52 的 bilingual **新** → cron 判定 pending
2. 08:49 `.allow-any-asr` marker 落地 → cron 每輪都挑中它
3. 每次 run 先燒完 修稿 + glossary + 分塊翻譯 的大量 LLM 呼叫，**然後**才會寫出結果 —— 但 Worker
   總在寫出前被外部中止 → `last-run.json` 永遠不存在（事故期間全程 404，這正是「看不見」的原因）
4. `finally` 在外部中止時不執行 → `.translating` 鎖殘留 → 10 分鐘 stale 過期 → 重試 → 回到 3
5. 加上這之前的 5 次手動嘗試（`?wait=1` 同步、`waitUntil` 非同步 ×3、切片重試），每次都是
   「錢燒完、產出丟掉」—— 錢花在**重複計算同樣的失敗**上

**止血動作**（當日）：重新 ingest 創作者 zh-Hant 軌蓋掉 source（zh 軌不看 marker 一律拒收，
cron 下一輪即跳過、零 LLM 花費）；`wrangler.jsonc` 的 `triggers.crons` 清空（合併部署後 cron 徹底停）。

**教訓**：花錢的迴圈必須有**花費側的保險絲**，不能只靠工作側的鎖 ——
鎖能防並發，防不了「每次都失敗但每次都全額付費」的重試。嘗試次數上限（第 2 點修法）是硬需求，不是優化。

### 建議的修法（尚未實作）

1. **分段可續跑**：修稿與翻譯拆成不同 cron 輪次，各自存中繼結果（`sentences.json` 已是天然檢查點），
   單輪工作量減半；kvsplayer 用 Queues 的分段掃描解同一個問題
2. **鎖要能自我修復**：縮短 stale 門檻，或在鎖裡記錄「第幾次嘗試」，連續失敗時降級（縮小 chunk）
3. **每階段落地進度**：cron 開工即寫 `last-run.json` 的 `status: running`，才能區分
   「沒被選中」與「選中後死掉」

## 5. 決策建議

**開放日文（及其他有標點的非英文）ASR**，理由：輸入品質足夠、錯誤型態正好是修稿 pass 的標的、
且失敗是**可見的**（產品名錯誤會直接顯示在對照的原文行，使用者一眼看得到）。

但**先修基礎設施**：現在就算開放閘門，長影片仍然跑不完 —— 這才是當前真正的瓶頸。
韓文維持保守（未量測），等有樣本再測。
