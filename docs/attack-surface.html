一個路人開了 ytplayer 會走到哪

結論先講：沒有連結的路人拿不到任何影片，也沒有任何寫入路徑進得去。曝險只有一種——拿到 /watch/{id} 連結的人看得到那支片。原本連「花了多少錢、模型吐了什麼」都一起送出去，那三項已經收掉了；剩下的字幕本體是刻意的取捨。

01四段動線

從網址列到資料，中間有四道關卡。每一道擋掉的東西不一樣。

  1. 01

    Cloudflare 邊界

    zone 層 WAF Managed Challenge ＋ Super Bot Fight Mode。實測 / 用 Chrome UA 與 curl UA 都回 403 challenge，/health 兩種都放行——規則是路徑限定的，只守頁面。真人會看到一次過場，之後靠 cookie 直接進。

  2. 02

    Worker 的爬蟲閘門

    只擋頁面，而且只看 User-Agent：自稱 GPTBot／CCBot／scrapy／空 UA 的一律 403，正牌搜尋引擎放行——要讓它讀得到 X-Robots-Tag: noindex，擋掉反而會被收錄。

  3. 03

    路由與認證

    寫入端點一律要 key（header；?key= 只認頁面路由）。/admin 另有 Cloudflare Access SSO。清單資料要 key，單片播放刻意公開——連結才好分享。

  4. 04

    資料層

    R2 沒有公開 bucket，只有 binding。對外唯一的路是 /subs/{11 碼}/{白名單檔名}，而且 content-type 由 Worker 決定（.srt → text/plain，其餘 → application/json），不跟著物件走——所以塞不出 text/html。

兩條路人動線的差別只在有沒有連結。沒有連結：開 / → 頁面骨架載入 → 前端打 /videos.json → 403 → 出現輸入金鑰的提示。拿不到任何 videoId，等於什麼都看不到。有連結：/watch/{id} 整頁可用，字幕、逐句稿、原文全部看得到——這是設計上接受的取捨。

03三個收斂：功能一點都沒少

沒有「路人能造成損害」的路徑（寫入全部要 key）。以下是讀取面給得比需要的多的三處，2026-09-04 全部收掉——重點是三個都沒有犧牲任何功能。

status.json 只剩進度三欄

原本拿到一條 watch 連結，就順便看得到這支片用了多少 token、哪個模型、失敗原因是什麼。而 failReason 會帶模型輸出的開頭——那是外部可控內容（字幕可以被 prompt injection）。

做法：公開版只回 stage／step／failed。player 頁照樣顯示失敗原因——它改成「localStorage 有金鑰就帶上」，同源請求加 header 不觸發預檢，零成本。自己人看完整版，路人看進度。

/health 不再報今日用量

原本任何人都看得到你今天翻了幾支、花掉多少 token。ingestKeyConfigured 更直接——它若是 false，等於公告「這站現在誰都能寫」。

做法：公開版只留 service／ok。ext 的分層診斷照樣能用，它只看 service === 'ytplayer'。用量要 key：curl -H "x-ingest-key: …"。

source.json 整份移出白名單

原始字幕軌加影片描述前 2000 字，是公開資料量最大的一份——而 player 一個欄位都沒用到。沒有使用端的東西，遮蔽不如不給。

做法：要 key 才拿得到。本機的 ab-runner 改成帶 INGEST_KEY，沒設會明講「需要金鑰」而不是回一個莫名其妙的 404。

更早之前處理掉的：字幕 → XSS → 偷金鑰

字幕是外部可控輸入。原本 failReason 會被塞進 /watch 的 innerHTML，而同源的 localStorage 存著 INGEST_KEY——完整鏈路成立。2026-08-21 補上 escape、?key= 限定頁面路由、CSP（connect-src 'self' 讓被注入的腳本也送不出去）。

04這張表是怎麼驗出來的

沒有 Cloudflare API token，也沒有 R2 憑證。所以能驗的與不能驗的，界線很清楚。

讀原始碼
路由表、認證判斷、白名單、content-type 決定邏輯——這些是事實，不是推測
本機假替身
測試跑的是 in-memory 的 FakeR2／FakeQueue，從來沒碰過真的 R2
公開端點
/subs/{id}/* 本來就對外，curl 直接量得到——這也正是它們「公開」的證明
金鑰端點
用你貼在對話裡的 INGEST_KEY 打過 /videos.json 與 /jobs.json。這就是它該換掉的理由
驗不到的
R2 dashboard 有沒有開 public access、WAF 規則的實際表達式、SBFM 的設定——全都要你去看
殘餘風險維持不變、且已接受：拿到 /watch/{id} 連結的人看得到那支片。要關掉這條，得讓 /watch 也走 key-gate——但那就不能分享了，是另一個取捨。這次收的是「連結之外還多送了什麼」，不是這條本身。
