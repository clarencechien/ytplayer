# 實驗計畫與結果：F1–F4／G1 上線後的補測（2026-08-16）

> 起因：F1–F4 + G1 的程式都上線了，但「測過的」與「只有單元測試的」不一樣。
> 這份把**還沒用真模型驗過的**項目列成有預算、有 gate 的實驗，一次跑完。
> 方法一律照 [model-reeval-sop.md](model-reeval-sop.md)：本機 runner、不碰 production。

## 計畫

| 編號 | 要驗什麼 | 設計 | Gate | 預算 |
|---|---|---|---|---|
| **E1** | F4：真實 YouTube 頁真的有 `videoDetails.channelId` | 抓觀看頁 HTML → 跑 ext 的 balanced-brace 抽取 | 合法 ucid 且 videoId 相符 | NT$0 |
| **E2** | G1：channel 鎖定表對模型有實際約束力 | 同一支片，注入 3 條 channel 術語 vs 無表對照 | 鎖定譯法出現率明顯高於無表 | ~NT$6 |
| **E3** | 3.6-flash 重評（F1 上線 = 當初禁用它的前提已備妥） | 3.6-flash × 3 次，與 3.5-flash 基準比 | `echoRejects` 不顯著高於 3.5、untranslated ≤ 基準 | ~NT$21 |
| **E4a** | F2：lite + 位置對齊協定 | lite + `TRANSLATE_PROTOCOL=array` + chunk 15 × 3 | untranslated = 0、成本降 ≥60% | ~NT$8 |
| **E4b** | F2 的對照組：lite + id 協定 | lite + chunk 15 × 3 | —（純對照，分離「模型」與「協定」兩個變因）| ~NT$8 |

樣本固定 `hK9fypJKHyY`（英 ASR 274 句）。基準沿用當天已量的
3.5-flash v5 六次（mean：untranslated 0、tokens 49.8k、NT$6.25、echoRejects 7–82）。

## E1 — F4 的資料路徑（**無法在容器內驗證**）

| 方法 | 結果 |
|---|---|
| `fetch()` 抓觀看頁 | **HTTP 429**（3.2 KB 擋頁，沒有 `ytInitialPlayerResponse`）|
| 無頭 Chromium 直連 | `ERR_CONNECTION_RESET` |

結論：YouTube 擋 datacenter IP —— 這正是 [pwa-plan.md](pwa-plan.md) §4 決定**不做伺服器端抓字幕**的同一道牆，
在這裡等於再次確認了那個決定，但 **F4 本身沒被驗證**。

風險已用程式面壓住：欄位是選填、ext 端與 Worker 端各有一次 `/^UC[\w-]{22}$/` 檢查、
抓不到就不帶欄位並自動退回名稱 slug（E2 實測走的就是這條後備路徑）。
**剩下的 30 秒人工驗收**：`chrome://extensions` 重新載入 ext → 送一支片 →
看 `/subs/{id}/source.json` 的 `meta.channelId` 有沒有出現。

## E2 — G1 channel 鎖定表（**通過**）

注入 `glossary/channel-9to5google.json`（3 條），對照組是同片同設定但沒有這個檔：

| 術語 | 有表 | 無表 |
|---|---|---|
| Pixel Tag → 「Pixel Tag 追蹤器」 | **6 / 7 句** | 0 / 7 句 |
| UWB → 「UWB 超寬頻」 | 1 / 3 句 | 0 / 3 句 |
| Find Hub | 原文 0 句（ASR 沒出現這個寫法）| — |

- 疊層合併正確：`layers = {channelKey:'9to5google', channel:3, genre:0, auto:15, merged:18}`
- **channel key 走的是名稱 slug**（舊 source 沒有 ucid）—— 後備路徑實測有效
- 結論：**人工表對模型有實際約束力**，「好譯法能沉澱」的機制成立

UWB 只中 1/3 的原因值得記一筆：另兩句的譯文根本沒提到 UWB —— 模型把語意重新分配到
相鄰 cue（子句邊界漂移），不是不聽術語表。**這也再次證實 F1 的回聲對位管不到漂移**
（那兩句的 `t` 是對的，錯的是內容分配）。

## E3 — 3.6-flash 重評（**維持禁用，但理由換了**）

| | 3.5-flash v5 | 3.6-flash v5 |
|---|---|---|
| untranslated | 0（6 次）| 0 / 2 / 0 |
| echoRejects | 7 / 11 / 82 | 15 / 72 / 39 |
| tokens | 49.4k | 66.4k（**+34%**）|
| 成本（3.6 輸出單價較低）| NT$6.08 | NT$6.41 |
| 耗時 | 30 秒 | **136 秒（4.5 倍）** |

判讀：
- **沒有任何一項贏**。單價便宜被 +34% 的 token 量吃光，還慢 4.5 倍、未譯更多
- `echoRejects` 與 3.5 同量級（沒有更糟）→ 回聲對位確實把它當年的「對滑」壓住了，
  但**壓住不等於值得換**
- 一次 JSON 解析失敗（chunk 6 輸出截斷，20 句一次進補救流程）

**結論：維持 `gemini-3.5-flash`。3.6 的禁用理由從「會譯錯句」更新為「沒有優勢：更慢、更貴、未譯更多」。**
（前者已被 F1 擋住，後者是新證據 —— 這正是重評的意義。）

## E4 — F2：lite × 協定（**假說成立，但仍不改預設**）

**控制變因只有協定**（同樣 lite、同樣 chunk 15）：

| | lite + id | lite + 位置對齊 |
|---|---|---|
| retries | 31–41 | **2–9** |
| tokens | 122k | **48.7k（-60%）** |
| warnings | 2–5 | 0–2 |
| untranslated | 1–4 | 0–1 |
| 成本 | NT$2.69 | **NT$0.89（-67%）** |

**「lite 缺句的病根是 index-keyed 協定對 id 紀律的要求，不是能力」——假說成立。**
把 id 拿掉、改用長度硬檢查後，lite 的重試次數掉到 1/6、token 掉到 4 成。

過程中修了一個實際缺陷：位置對齊無法部分成功，原本只切半一次，
一個壞掉的半包 = 連續 7 句沒翻（e4a 第 3 輪）。**改成多切一層**（`maxDepth`／`minSplit` 依協定分開）後
未譯降到 0–1。

人工抽樣（兩個 15 句視窗，逐句核對原文與譯文對位）：
lite 的譯文**對位正確、可讀**，語感比 flash 略鬆（例：flash「旗鼓相當」vs lite「一樣」），
沒有簡體、沒有中國用語殘留。

**決策：預設仍是 3.5-flash。** 理由不是成本，是這個專案的目標
（品質明顯高於 YouTube 自動翻譯）：flash 6 次全 0 未譯、語感更好，一片 NT$6 在每月幾支的用量下不是問題。
但 lite + 位置對齊**已經是可用選項**，適用場景很明確：

> **要大量補翻舊片時**（cost-optimization.md 一直掛著的那個前提），
> `TRANSLATE_PROTOCOL=array CHUNK_SIZE=15` + lite = 一片 NT$0.89、15 秒，
> 品質可接受、失敗看得見。100 支片 NT$89 vs NT$608。
