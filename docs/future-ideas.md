## F1. 回聲對位（echo alignment）— 根治子句邊界漂移

### 動機（有實據）
`cost-optimization.md` §8：長原文配極短譯文、連續數句位移一格。**舊版 3 句、新版 5 句**——
既有現象，目前只有 `driftSuspect` 在數它（進 hints），沒有修它。
同一母題也涵蓋 3.6-flash 的「id 對滑」（`model-experiment.md`），那是我們禁用 3.6 的原因。

### 設計草案
翻譯輸出格式加一個回聲欄位，讓「這句譯文對應哪句原文」變成**可驗證**而不是靠信任：

```jsonc
// 現行： {"id":12,"zh":"譯文"}
// 改為： {"id":12,"t":"I think it is","zh":"譯文"}   // t = 原文前 12 個字元
```

- 驗證：`t` 與 `targets.get(id)` 的前 12 字元比對（正規化空白/大小寫）；**對不上就丟棄該筆**
  → 該句進入既有的補丁式重試流程（L1 已經很便宜）
- 成本：每句多 ~6–10 個輸出 token（274 句 ≈ +2k tokens ≈ NT$0.6/片）——
  用 L1 省下的 NT$5.5 換這個保險，划算
- 沿用 sukemu 已驗證的做法（`gemini-api-lessons` §6「t 回聲對位」）

### 驗收 Gate
1. **先量自然變異**：同設定（現行程式）跑同一支片 **3 次**，記錄 `driftSuspect` 命中數的分布
   —— 沒有這把尺，就無法宣稱回聲對位「有效」（`gemini-api-lessons` §2 的 A/B 方法論）
2. 回聲版跑 3 次，命中數需**顯著低於**基準分布
3. `untranslated` 不得增加；tokens 增幅 ≤ 10%
4. 抽樣 10 句人工比對：被丟棄重試的句子確實變準（不是只是換個錯法）

### 成本／風險
半天。風險低（純協定加欄位，失敗就退回既有行為）。
**唯一要注意**：`t` 也可能被模型「編」出來對上——所以比對要用原文而非模型的自述，
且丟棄邏輯要保守（對不上就丟，不試圖猜哪句才對）。

---

### ✅ 實測結果（2026-08-16，`hK9fypJKHyY` 英 ASR 274 句，各 3 次以上）

| 指標 | 基準（v4，只靠 id） | 回聲版（v5） | 判讀 |
|---|---|---|---|
| `untranslated` | 0 / 0 / 0 | 0（6 次全 0） | 沒有副作用 ✅ |
| `driftSuspect` | 2 / 2 / 3（mean 2.33） | 4/1/3/3/3/6（mean 3.33） | **沒改善**，且落在雜訊裡 ❌ |
| tokens | 39.5k / 51.0k / 41.1k（mean 43.8k） | mean 49.8k | **+14%** ❌（gate 訂 ≤10%） |
| 成本 | mean NT$5.40 | mean NT$6.25 | +NT$0.85／片 |
| `echoRejects`（新指標） | —（協定不存在） | 82 / 7 / 11（mean 33） | 確實在攔 ✅ |

**人工抽樣（gate 第 4 項）**：抓一個 40 句的 chunk 逐句比對模型回的 `t`，
3 句對不上、且是**連續整段位移一格**的典型對滑：

```
#35 原文「internal accelerometer. It's got a」
#36 原文「built-in speaker as well that can be」  ← 模型回 t=「It's got a」（是 #35 的尾巴）
#37 原文「remotely triggered to play loud locating」← 模型回 t=「built-in spe」（是 #36）
#38 原文「tones like any other tracker out there.」← 模型回 t=「remotely tri」（是 #37）
```

沒有回聲欄位的話，這三句會被靜靜地收下 —— 譯文通順、id 連號、自動指標全綠，
但字幕對到隔壁句。**這就是 F1 存在的理由，而且它在正式模型的正常輸出裡真的會發生。**

### 日文 ASR 的代價（`9gHJwbSHPus`，679 句，各 1 次）

| | production v4（線上既有結果） | v5 回聲版 |
|---|---|---|
| `untranslated` | 0 | **4**（0.6%） |
| warnings | 1 | 5 |
| `echoRejects` | — | **127 句次（19%）** |
| 成本 | 未記錄 | NT$23.4 |

日文 ASR 的 cue 常在子句中間斷開，模型更容易「翻的是隔壁碎片」——
攔截率因此高得多。被攔下又補不回來的 4 句會以**原文顯示並標記 untranslated**。

**這是刻意的取捨**：本專案的品質地板原則是「寧可看得見地失敗，也不要安靜地錯」
（開發原則 #2）。4 句看得出沒翻 > 4 句通順但對到隔壁句。
若日後覺得日文的攔截太兇，旋鈕在 `pipeline.ts` 的 `ECHO_LEN`（放寬比對長度）
或直接拿掉 prompt 的 t 欄位段落（解析端本來就相容）。

### 原設計錯在哪（必須修正的假設）

1. **把「子句邊界漂移」和「id 對滑」當成同一件事** —— 不是。
   漂移是模型把語意重新分配到相鄰 cue（`driftSuspect` 數的是這個），回聲對位管不到，
   實測也確實沒降。要修漂移得走別的路（例如把相鄰碎片合併成完整句再翻）。
2. **成本估太樂觀**：原估 +2k tokens（+4%），實測 +14% ——
   因為多出來的不只是 `t` 欄位本身，還有**被攔下的句子要重譯**（每片 7–82 句次）。
3. **gate 第 2 項用錯尺**：該看的是 `echoRejects` 與人工抽樣，不是 drift 命中數。

### 決策

**維持開啟**（2026-08-16）：+NT$0.85／片換「字幕不會對到隔壁句」，在自用規模下划算；
gate 的 tokens 上限沒過是因為原估算沒把重譯算進去，不是行為失控。
反悔成本很低：把 `prompts.ts` 的 t 欄位段落拿掉即可（解析端本來就相容「模型不回 t」）。

## F2. lite 級翻譯換協定（按位置對齊）

### 動機（有實據）
`model-experiment.md`：`gemini-3.5-flash-lite` 缺 27 句、縮 chunk 到 20 反而更糟（30 句）。
病根不是 batch 大小，是 **index-keyed 協定對 lite 的 id 紀律要求太高**。
但 lite 的牌價是 flash 的 1/5（$0.30/$2.50 vs $1.50/$9.00）——**成功則單片再砍 ~6 倍**。

### 設計草案
把「靠 id 對齊」換成「靠位置對齊」，讓模型不必維持 id 紀律：

```jsonc
// 輸入：一句一行，不給 id
// 輸出：純字串陣列，第 n 個元素 = 第 n 句的譯文
["譯文一", "譯文二", "譯文三"]
```

- 驗證：**長度必須完全等於輸入句數**，否則整包丟棄重試（比 id 檢查更硬、更好驗）
- 缺點：無法部分成功（少一句就整包重來）→ 所以**必須配小 chunk（10–15 句）**
- 與 F1 可疊加：位置對齊 + 回聲欄位 = 雙保險（但輸出成本上升，先單獨驗證）

### 驗收 Gate
- 同片 A/B：lite+位置協定 vs 現行 flash+id 協定，`untranslated` 必須 **= 0**
- 抽樣 15 句人工比對（lite 的譯文品質本身也要看，不只是有沒有缺）
- 成本下降 ≥ 60% 才算划算（否則不值得維護第二套協定）

### 成本／風險
一天（含 prompt 改寫、驗證器、兩套協定並存的分支）。
**風險：維護兩套輸出協定**。若 lite 品質過關但差距不明顯，寧可不做——
單一協定的可維護性 > 省下的錢（自用規模下）。

---

### ⚠ 實作狀態（2026-08-16）：程式好了，**預設關閉**

```bash
TRANSLATE_PROTOCOL=array CHUNK_SIZE=15 node /tmp/ab-runner.mjs <videoId> gemini-3.5-flash-lite /tmp/ab/lite --repeat 3
```

- `buildTranslateArrayPrompt` + `parseArrayOutput`：長度不等於輸入句數就**整包丟棄**
  （模型少一句、多一句、把兩句合併，全被這一行擋下），其餘走既有的重打／切半分治
- 品質地板照舊（`sanityCheckItem`、禁用詞掃描逐句生效）
- **沒有回聲欄位**：位置對齊本身就是對位保證（沒有 id 可滑）
### ✅ 已驗證（2026-08-16，見 [exp-2026-08-16.md](exp-2026-08-16.md) E4）

**核心假說成立**：控制變因只有協定（同 lite、同 chunk 15），
重試 31–41 → 2–9 次、tokens 122k → 48.7k（-60%）、成本 NT$2.69 → 0.89（-67%）。
lite 缺句的病根確實是 index-keyed 協定對 id 紀律的要求，不是能力問題。

| gate | 結果 |
|---|---|
| `untranslated` = 0 | 0 / 0 / 1 —— **差一點**（flash 是 6 次全 0）|
| 成本降 ≥ 60% | **-85%**（NT$6.08 → 0.89）✅ |
| 人工抽 15 句 | 對位正確、可讀，語感比 flash 略鬆 ✅ |

過程中修掉一個真缺陷：位置對齊無法部分成功，原本只切半一次 →
一個壞掉的半包等於連續 7 句沒翻。改成**依協定多切一層**後未譯降到 0–1。

**決策：預設仍是 3.5-flash**（品質目標優先，每月幾支片的用量下 NT$6/片不是問題），
但 lite + 位置對齊已是**大量補翻舊片的可用選項**：100 支片 NT$89 vs NT$608。

## F4. ext 抓 channelId（ucid）

### 動機
`glossary-layers.md` 的 channel 疊層需要穩定的頻道鍵值，但 ext 目前只抓頻道**名稱**——
名稱可改、可重複。這件事本身很小，卻是 glossary 疊層 G1 的品質前提。

### 設計草案
- ext 從 `ytInitialPlayerResponse.videoDetails.channelId`（`UC...`）取得 ucid，
  放進 ingest payload 的 `meta.channelId`
- `validate.ts` 加選填欄位驗證（`/^UC[\w-]{22}$/`）
- glossary channel key 改用 ucid；已存在的名稱 slug 檔案寫一次性對照表遷移
- **舊 source 沒有這個欄位** → 沿用名稱 slug，兩種鍵值並存查找（先 ucid 後名稱）

### 驗收
- 新 ingest 的 payload 帶 `meta.channelId`；舊片不受影響
- 頻道改名後，glossary 鎖定表仍然命中

### 成本
1–2 小時。風險極低（純新增選填欄位）。**建議與 glossary 疊層 G1 同批做**，
單獨做沒有可見效益。

### ✅ 已上線（2026-08-16，與 G1 同批）
`bridge.js` 抓 `videoDetails.channelId`（自帶 `/^UC[\w-]{22}$/` 檢查，抓不到就不帶欄位）→
`validate.ts` 選填驗證 → `channelKeys()` **ucid 優先、名稱 slug 後備**兩種鍵值並存查找。
細節與差異見 [glossary-layers.md](glossary-layers.md) §3、§7.1。
**要生效需在 `chrome://extensions` 重新載入 ext**（舊 payload 不會有這個欄位）。
