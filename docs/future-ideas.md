## F1. 回聲對位（echo alignment）— 根治子句邊界漂移

### 動機（有實據）
`cost-optimization.md` §8：長原文配極短譯文、連續數句位移一格。**舊版 3 句、新版 5 句**——
既有現象，目前只有 `driftSuspect` 在數它（進 hints），沒有修它。
同一母題也涵蓋 3.6-flash 的「id 對滑」（`model-experiment.md`），那是我們禁用 3.6 的原因。

### 設計草案
翻譯輸出格式加一個回聲欄位，讓「這句譯文對應哪句原文」變成**可驗證**而不是靠信任：

```jsonc
// 現行： {"id":12,"zh":"譯文"}
// 改為： {"id":12,"t":"I think it is","zh":"譯文"}   // t = 原文前 12 個字元
```

- 驗證：`t` 與 `targets.get(id)` 的前 12 字元比對（正規化空白/大小寫）；**對不上就丟棄該筆**
  → 該句進入既有的補丁式重試流程（L1 已經很便宜）
- 成本：每句多 ~6–10 個輸出 token（274 句 ≈ +2k tokens ≈ NT$0.6/片）——
  用 L1 省下的 NT$5.5 換這個保險，划算
- 沿用 sukemu 已驗證的做法（`gemini-api-lessons` §6「t 回聲對位」）

### 驗收 Gate
1. **先量自然變異**：同設定（現行程式）跑同一支片 **3 次**，記錄 `driftSuspect` 命中數的分布
   —— 沒有這把尺，就無法宣稱回聲對位「有效」（`gemini-api-lessons` §2 的 A/B 方法論）
2. 回聲版跑 3 次，命中數需**顯著低於**基準分布
3. `untranslated` 不得增加；tokens 增幅 ≤ 10%
4. 抽樣 10 句人工比對：被丟棄重試的句子確實變準（不是只是換個錯法）

### 成本／風險
半天。風險低（純協定加欄位，失敗就退回既有行為）。
**唯一要注意**：`t` 也可能被模型「編」出來對上——所以比對要用原文而非模型的自述，
且丟棄邏輯要保守（對不上就丟，不試圖猜哪句才對）。

## F2. lite 級翻譯換協定（按位置對齊）

### 動機（有實據）
`model-experiment.md`：`gemini-3.5-flash-lite` 缺 27 句、縮 chunk 到 20 反而更糟（30 句）。
病根不是 batch 大小，是 **index-keyed 協定對 lite 的 id 紀律要求太高**。
但 lite 的牌價是 flash 的 1/5（$0.30/$2.50 vs $1.50/$9.00）——**成功則單片再砍 ~6 倍**。

### 設計草案
把「靠 id 對齊」換成「靠位置對齊」，讓模型不必維持 id 紀律：

```jsonc
// 輸入：一句一行，不給 id
// 輸出：純字串陣列，第 n 個元素 = 第 n 句的譯文
["譯文一", "譯文二", "譯文三"]
```

- 驗證：**長度必須完全等於輸入句數**，否則整包丟棄重試（比 id 檢查更硬、更好驗）
- 缺點：無法部分成功（少一句就整包重來）→ 所以**必須配小 chunk（10–15 句）**
- 與 F1 可疊加：位置對齊 + 回聲欄位 = 雙保險（但輸出成本上升，先單獨驗證）

### 驗收 Gate
- 同片 A/B：lite+位置協定 vs 現行 flash+id 協定，`untranslated` 必須 **= 0**
- 抽樣 15 句人工比對（lite 的譯文品質本身也要看，不只是有沒有缺）
- 成本下降 ≥ 60% 才算划算（否則不值得維護第二套協定）

### 成本／風險
一天（含 prompt 改寫、驗證器、兩套協定並存的分支）。
**風險：維護兩套輸出協定**。若 lite 品質過關但差距不明顯，寧可不做——
單一協定的可維護性 > 省下的錢（自用規模下）。

## F3. 模型重評的觸發條件（3.6 / 3.7 / 未來新版）

### 動機
`model-experiment.md` 記著 3.6-flash 因 id 對滑禁用、3.7-flash 因無 `minimal` 檔位觀望。
但這些結論會過期——需要明確的「什麼時候該重測」，否則要嘛永遠不動、要嘛憑印象亂換。

### 觸發條件（滿足任一即值得重測）
- **3.6-flash**：F1 回聲對位上線後（它正是為了擋 id 對滑而生）——前提已備妥就該重測
- **3.7-flash**：官方為它加上 `minimal` 檔位，或社群出現 batch JSON 翻譯的實測數據
- **任何新模型**：3.5-flash 被標為 deprecated，或牌價變動 > 30%

### 重測 SOP（每次都一樣，不要臨場發明）
1. `POST /translate/{id}?force=1&model=…` 跑兩支固定樣本（`hK9fypJKHyY` 英、`9gHJwbSHPus` 日）
2. **同設定重複 3 次**量自然變異，再比候選
3. 硬指標：`untranslated`、`warnings`、`driftSuspect` 命中數、tokens、成本
4. **軟指標（不可省）**：抽樣 10–15 句人工比對——id 對滑與「穩定地錯」自動指標測不到
5. 結論回填 `model-experiment.md`，勝出者才改 `wrangler.jsonc`

### 成本
每次重測約 NT$20（4 組 × 2 支，本機 ab-runner 跑不影響 production）。

## F4. ext 抓 channelId（ucid）

### 動機
`glossary-layers.md` 的 channel 疊層需要穩定的頻道鍵值，但 ext 目前只抓頻道**名稱**——
名稱可改、可重複。這件事本身很小，卻是 glossary 疊層 G1 的品質前提。

### 設計草案
- ext 從 `ytInitialPlayerResponse.videoDetails.channelId`（`UC...`）取得 ucid，
  放進 ingest payload 的 `meta.channelId`
- `validate.ts` 加選填欄位驗證（`/^UC[\w-]{22}$/`）
- glossary channel key 改用 ucid；已存在的名稱 slug 檔案寫一次性對照表遷移
- **舊 source 沒有這個欄位** → 沿用名稱 slug，兩種鍵值並存查找（先 ucid 後名稱）

### 驗收
- 新 ingest 的 payload 帶 `meta.channelId`；舊片不受影響
- 頻道改名後，glossary 鎖定表仍然命中

### 成本
1–2 小時。風險極低（純新增選填欄位）。**建議與 glossary 疊層 G1 同批做**，
單獨做沒有可見效益。
