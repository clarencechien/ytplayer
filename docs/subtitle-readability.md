# 字幕可讀性：CPS、行長、行數（R1–R4）

> 狀態：**計畫，未實作**。決策欄在 §8。工作量約**兩天半**
> （R1 半天 + R2 一天 + R3 半天 + R4 半天）。
> 起因：2026-08-17 盤點「斷句跟人做的不一樣」時，量出我們在**尾巴 3%** 的句子上
> 同時違反三條業界規範。
> 先查過有沒有現成 skill 可用（字幕／翻譯／在地化）—— **沒有**，所以照規範自己做。

## 1. 業界規範（Netflix 繁中 Timed Text Style Guide）

| 項目 | 規範 | 為什麼 |
|---|---|---|
| 每行字數 | **≤ 16 全形字** | 視線橫掃的極限 |
| 行數 | **≤ 2 行** | 超過會遮畫面、眼睛要上下找 |
| 閱讀速度 | **≤ 9 字/秒（CPS）** | 中文字資訊密度高 —— 英文是 20 字元/秒 |
| 單塊時長 | 5/6 秒 ～ 7 秒 | 太短來不及讀、太長會以為卡住 |

來源：[Netflix zh-Hant Timed Text Style Guide](https://partnerhelp.netflixstudios.com/hc/en-us/articles/215994807-Chinese-Traditional-Timed-Text-Style-Guide)、
[閱讀速度怎麼算](https://partnerhelp.netflixstudios.com/hc/en-us/articles/115001352212-How-is-reading-speed-measured-Do-punctuation-and-spaces-count)（標點與空白都算）

## 2. 我們現在的狀況（2026-08-17 實測 production 資料）

| | 中文字數中位數 | p90 | 最長 | 顯示秒數中位數 | 最長 |
|---|---|---|---|---|---|
| `JM-oaFXgaSg`（119 句）| 12 | 17 | 29 | 2.8s | 8.3s |
| `kCIvgJklMWQ`（512 句）| 13 | 22 | 44 | 2.5s | 14.0s |

**大部分是健康的**（中位數 12–13 字遠低於 16）。問題全在尾巴：

```
2.0 秒 | 正如其名，這棟房子周邊自然環境非常豐富，視野也極佳，今天就來帶大家參觀。
```

36 字 ÷ 2.0 秒 = **18 CPS（規範上限的兩倍）**，而且 36 字要 3 行才放得下。
`kCIvgJklMWQ` 有 18 句（3%）≥28 字，另有單句掛 14 秒的（規範上限 7 秒）。

**病灶有三個，彼此獨立**：

| 病灶 | 現象 | 修法 |
|---|---|---|
| 譯文太長，時間根本不夠讀 | 18 CPS | **R1 壓縮譯文**（prompt 給字數預算）|
| 譯文長度合理，但一行塞不下 | 36 字擠成一行 | **R2 顯示折行／拆塊** |
| 看外語時想回頭看前一句 | 前一句瞬間消失 | **R3 前一句留著**（產品決策）|

## 3. R1 — 壓縮譯文（prompt 給字數預算）· 半天

**這是產業對「時間不夠讀」的真正答案**：專業字幕師的核心技能就是砍冗詞把資訊
塞進 CPS 上限，Netflix 明文預期譯者這樣做。而這件事**模型完全做得到** ——
它缺的只是「這句有幾秒」這個資訊，而我們手上就有。

### 設計

```ts
// segment.ts 的 Sentence 在詞級斷句時自帶 start/end
const budget = clamp(Math.round((s.end - s.start) * 9), 8, 32);
// prompt 每句標上：  12 (≤14 字): I think it is a very good option for a
```

- **9 CPS** 直接取規範上限（我們的目標是「讀得完」，不是「輕鬆讀」）
- 下限 8：太短的預算會逼出不自然的電報體
- 上限 32 = 2 行 × 16 字：再長就是 R2 的責任
- **只在時間可靠時給**：詞級斷句（`segs`）算出來的 start/end 才準；
  video 路由的時間軸是模型估的，**不給預算**（假的預算比沒有更糟）

### 為什麼不「超標就重譯」

超標的句子重譯一次要多付一次 API —— 而它**本來就已經是可用的譯文**，只是讀起來趕。
沿用既有原則：`hints` 記下來讓它可見（`N 句超過 9 CPS`），不自動花錢修。
真的想修，`/patch` 已經是現成的手動工具。

### 驗收 Gate

1. 先量自然變異（同設定 3 次，記 CPS > 9 的句數）—— 照 [model-reeval-sop.md](model-reeval-sop.md)
2. 加預算後 CPS > 9 的句數**顯著低於**基準分布
3. `untranslated` 不增加；tokens 增幅 < 5%（prompt 只多幾個字元）
4. **抽樣 10 句人工比對**（不可省）：確認模型是「砍冗詞」而不是「砍語意」——
   這是本項最大的風險，自動指標測不到

### 成本／風險

半天。API 成本增加近乎零。
**風險：模型為了湊字數而丟掉資訊**。所以 gate 4 不能省，而且預算是**上限不是目標**
（prompt 要寫「≤N 字」而不是「N 字」）。

## 4. R2 — 顯示折行與拆塊 · 一天

分成三段，難度遞增：

### (a) player 折行（零風險，先做）
中文超過 16 字自動折成兩行。純 CSS/排版，不動資料。
⚠ 我們的兩行已經被「中文 + 原文」用掉了 —— 中文折兩行 = 畫面三行。
**折不折要看 R3 的行數預算**（§5）：預算夠就折，不夠就縮字級塞一行。
兩項共用同一套預算邏輯，所以 R2a 與 R3 應該一起做。

### (b) 超長句拆塊（動到 cue 結構，小心）
`36 字 / 6 秒` 這種**時間夠但一塊太長**的，拆成兩塊分次顯示（各 18 字 / 3 秒）：

- 切點：標點優先（，、；），沒有標點就找最接近中點的詞界
- 時間：按字數比例分配，兩塊都要 ≥ 最短顯示時長（`retime.ts` 的 `minDurFor`）
- **時間不夠的（36 字 / 2 秒）拆了也沒用** —— 那是 R1 的責任，這裡不碰

### (c) 冪等性（這是最容易出事的地方）
`retimeCues` 的冪等靠 `end0` 錨點，前提是**一句一 cue**。拆塊會破壞這個假設：
重跑「⏱ 修時間」會不會把已經拆過的再拆一次？

解法：拆出來的塊標記 `split: true` 並記 `srcId`，拆塊函式看到 `split` 就跳過。
**驗收必須包含「連按兩次修時間，結果完全相同」**。

### 不切在詞中間？
中文標點密度高，光靠標點就能處理絕大多數。真要詞界感知，
先試 `Intl.Segmenter`（V8 內建，**要先確認 Workers 的 ICU 有帶 word granularity**，
一分鐘可測）；不行就退回「不切在數字/英文單字中間」的簡單規則。
**不要為此引入外部斷詞服務**（見 §7）。

## 5. R3 — 前一句留著（roll-up）· 半天 · **產品決策**

使用者提的：「前一列不會馬上消失」。

- 這在業界確實存在，但定位是**直播字幕（live CC）**；預錄字幕的規範不建議
  （會佔畫面、觀眾容易分心）
- 有趣的是我們已經在 `ext/normalize.js` **主動跳過** YouTube 的 roll-up 列
  （`aAppend === 1`），因為那些列的內容是重複累積的
- **但我們的產品定位不同**：規範假設你在看戲，我們的使用者在**看外語學東西** ——
  前一句留著（淡化）是合理的閱讀輔助

### 設計：不是開關，是「行數預算」

「關掉原文才有空間放前一句」這個直覺是對的，但它其實是更一般規則的特例。
真正的限制是**畫面能給幾行**，而那隨情境變動：

| 情境 | 行數預算 | 理由 |
|---|---|---|
| 桌機／劇場模式 | 4 | 字幕在影片下方，空間充足 |
| 手機直向 | 3 | 字幕在影片下方，但螢幕窄 |
| 手機橫向（字幕疊畫面） | **2** | 疊在畫面上，多一行就是擋畫面 |

字幕區的組成：`[前一句（淡）] + [中文（可能折兩行）] + [原文]`

**超出預算時由下往上砍，順序是原則性的**：

```
1. 先砍「前一句」        ← 系統自動加的，砍掉不違背使用者意圖
2. 再砍「中文折行」      ← 改成縮字級塞一行
3. 原文永遠不砍          ← 使用者明確選了雙語模式，不能自動幫他關掉
```

**使用者明確選的東西不能被自動砍掉** —— 這條原則比任何排版規則優先。

### 設定項

`S` 面板加一個三態選項「前一句」：

| 值 | 行為 |
|---|---|
| **自動**（預設） | 行數預算有剩才顯示 —— 於是**關掉原文時它自然出現**，開雙語時自然消失 |
| 開 | 一律顯示（桌機想忍受四行的人） |
| 關 | 一律不顯示（維持現在的體驗） |

「自動」正是使用者要的行為，但用預算表達的好處是：手機橫向就算只留中文也不會
硬塞第二行，桌機開雙語也還有空間放前一句。

### 前一句的細節規則

- **間隔 > 5 秒就不顯示**：場景已經換了，留著上一句會誤導
- 只佔一行，超過就截斷加省略號（前一句是輔助，不是主角）
- 50% 透明度、小一級字
- 影片開頭沒有前一句時不留空白（不是塞空行，是不渲染）

### 加分項（可選，成本極低）

**點前一句 = 跳回去重播那句**。player 已經有 seek，這只是加個 click handler。
對「剛才那句沒聽清楚」的學習場景很有用 —— 而這正是本專案存在的理由。

### 驗收
- **四種字幕模式 × 三種情境**的實際行數都不超過預算
- 手機橫向最大化時不遮擋畫面
- 切換字幕模式時不閃爍、不跳版
- 影片開頭沒有前一句時不留空白

## 6. R4 — 對已翻好的影片套用（`/admin` 按鈕）· 半天

R1–R3 只影響「之後翻的片」，但**手上的片都已經翻好了**。
為了 3% 的句子整片重翻（`?force=1`）等於付 100% 的錢修 3% 的問題 —— 不合理。

### 這其實是本專案已經成形的模式

| 按鈕 | 機制 | 成本 |
|---|---|---|
| ⏱ 修時間 | deterministic 重算顯示時間軸（`retimeCues`）| 零 |
| ✏ 補譯 | 只重譯未譯／原文照抄的句子（`patchStep`）| 以句計價 |
| **✂ 修排版**（新） | deterministic 拆長句 + 重算時間 | **零** |
| **📏 壓縮過長句**（新） | 只重譯 CPS 超標的句子 | 以句計價（約 3%）|

**原則：每個品質改善都要有「事後套用」的路徑。**
語料已經翻好了，重跑整片是最貴也最笨的修法 —— 這條原則值得寫進 CLAUDE.md。

### R4a「✂ 修排版」= R2b 的事後版（零 LLM）

跟 ⏱ 修時間同一類：純函式、deterministic、冪等。
把 R2b 的拆塊邏輯抽成 `resplitCues(cues)`，`/admin` 加按鈕、`POST /resplit/{id}`。

- 拆完接著跑 `retimeCues`（兩者本來就該連著跑）
- 冪等靠 R2b 設計的 `split` 標記（見 §4c）——
  **驗收就是「連按三次結果完全相同」**
- 舊片沒有 `end0` 也沒關係，`retimeCues` 會自動補

### R4b「📏 壓縮過長句」= 把 `/patch` 一般化

不必寫新步驟 —— **`patchStep` 只差一個目標偵測器**：

```ts
// 現在：needsRetranslate(orig, zh, untranslated)   → 未譯／原文照抄
// 加上：exceedsCps(zh, start, end)                 → 字數 / 秒數 > 9
POST /patch/{id}?mode=untranslated|cps|all
```

其餘全部沿用：帶前後語境的小請求、上限 2 輪、warnings 重寫、四層保險絲。
重譯時把 R1 的字數預算一起丟進 prompt（同一段程式）。

- 成本：一支 500 句的片約 15 句超標 → 一次呼叫、NT$0.2 上下
- **模式預設是 `untranslated`**（維持現有行為）；`cps` 要明示 ——
  自動壓縮會改動使用者已經在看的譯文，那必須是人為決定
- 壓縮後仍超標的不再重試（同 §3「不自動花錢修」的原則），記 hint

### 驗收
- ✂ 修排版：連按三次結果相同；拆出來的塊都 ≤2 行；SRT 同步更新
- 📏 壓縮：只有超標句被改動（逐句 diff 驗證）、未譯數不增加、抽樣人工比對
- 兩顆按鈕都只在 `route === 'text'` 顯示（video 路由時間軸是模型估的，見 §3）

## 7. 明確不做

- ❌ **外部斷詞服務（CKIP-transformers 等）**：它是繁中斷詞/POS/NER，
  而我們的**斷句發生在原文側（英/日 ASR）**，用不上；就算用在中文切分，
  PyTorch + 幾百 MB 模型跑不進 Workers，得另養服務 —— 與自用規模不成比例
- ❌ **讓模型決定 cue 邊界**：它不知道時間軸，也看不到整片（分塊平行翻譯）
- ❌ **超標句自動重譯**：貴，而且原譯文本來就可用（見 §3）
- ❌ **自動改寫已翻好的舊片**：R1–R3 只影響之後翻的片。舊片**手動**套用走 R4 的兩顆按鈕
  （§6）—— 自動去改使用者已經在看的譯文，是不請自來的驚喜，不是功能
- ❌ **用 `?force=1` 修排版問題**：整片重翻 = 為 3% 的句子付 100% 的錢

## 8. 決策（人工填寫）

```
R1 壓縮譯文（prompt 字數預算）：____（做 / 不做）
R2a player 折行：____（做 / 不做）
R2b 超長句拆塊：____（做 / 不做 / 等 R1 之後再看還剩多少）
R3 前一句留著：____（行數預算 + 三態設定 / 只做簡單開關 / 不做）
   └ 點前一句跳回重播：____（一起做 / 之後再說）
R4a ✂ 修排版按鈕（零 LLM）：____（做 / 不做）
R4b 📏 壓縮過長句按鈕（/patch?mode=cps）：____（做 / 不做）
日期：____
理由：____
```

> 建議順序：**R1 → R2a+R3（共用行數預算）→ 重新量一次 → 再決定 R2b/R4**。
> R1 是唯一治本的（時間不夠讀就是不夠讀，排版救不了）；R2a+R3 共用預算邏輯要一起做；
> R2b 動到 cue 結構，等 R1 做完再看還剩幾句需要拆，很可能不用做 ——
> **而 R4 的工作量取決於 R2b 有沒有做**（R4a 是 R2b 的事後版，R4b 只是 `/patch` 多一個偵測器）。
